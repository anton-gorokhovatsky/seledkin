# Публикация одного поста

Правило пользователя от 27 октября 2026 года: выпуск поста занимает несколько
минут работы процесса. Проверки неизменённых разделов его не блокируют.
Очередь GitHub, получение исходников и уточнение отсутствующих данных могут
добавить время; это не основание запускать общий аудит сайта.

## Подготовка

1. Сверить полный текст, дату и фотографию с оригиналом. Новости и поставки
   идут в журнал, рецепты и советы — в `/recipes/`. Сохранить полный источник
   в `content/journal/<id>.html`; контактную подпись пометить
   `journal-source-signature`. Подтверждённые абзацы добавить в обычный
   `tests/fixtures/journal-<month>-<year>.json`.
2. Добавить запись в `content/journal.json`. Для продаваемого товара указать
   постоянные `catalogProductIds`; для рецепта действуют его `products`.
   Пригодность мобильной афише явно записать в `mobileHero.eligible` с причиной
   в `mobileHero.reason`. Если подходит, задать `heroOrderName` — подпись вида
   «ряпушку холодного копчения». При нескольких товарных связях явно выбрать
   одну через `mobileHero.productId`. Привязка и решение живут в данных,
   менять `site-content.mjs` ради нового поста не надо.
   Для рецепта заполнить существующие `products` в `content/recipes.json`.
   Новый товар или новую цену связать с источником этого поста в `source`.
   Десктопная `homeJournalEntries` следует жанру, мобильная `mobileHomeEntries`
   берёт пять свежих подходящих снимков независимо от жанра рецепта.
   Если подходит обеим задачам, обновляются обе формы; если только чтению —
   десктопная. Настоящая нетоварная история отмечается `editorialOnly: true`,
   без фиктивной товарной связи и с `mobileHero.eligible: false`. Продающий
   пост без каталога и цены остаётся ошибкой. Отдельный мобильный список
   не вести. При каждом обновлении сверить обе формы и записанное решение.
3. Сохранить исходное фото, собрать только его варианты и страницы:

   ```sh
   pnpm build:media --source=journal-703.jpg
   pnpm build:site
   node scripts/check-editorial-release.mjs --ids=703
   EDITORIAL_IDS='["703"]' pnpm exec playwright test --config=playwright.editorial.config.mjs
   ```

   Число 703 в примере заменяется номером нового поста. Локальный сценарий
   использует Chromium и WebKit; смотрим сам материал и его анонс, а не весь
   сайт. Для записи первого экрана этот же целевой прогон проверяет мобильное
   фото, цену, товарную ссылку и оба обращения; статический gate сравнивает
   сгенерированные подборки обеих форм. Рецензент проверяет готовые исходники
   и эти свидетельства один раз.
4. Сделать обычный коммит. До push проверить классификацию относительно
   последней успешной публикации. Ожидается `scope=editorial` и только ID
   затронутого поста. Для обычного поста не нужны `[skip ci]`, ручной обход
   проверок или отдельный workflow.

## Что блокирует редакционный выпуск

- Несогласованная сборка страниц или медиаманифеста.
- Потеря абзаца, даты, источника или фотографии именно выбранного поста.
- Отсутствующая точная позиция каталога, цена, ссылка или черновик заказа.
- Дефект выбранной страницы: кадрирование, переполнение, невидимый фокус,
  узкий экран, увеличение текста с интервалами или чтение без JavaScript.

CI запускает только `editorial-publication.spec.mjs` с `EDITORIAL_IDS`.
Это четыре случая для каждого выбранного поста: широкий экран с переходом
из анонса к товару и двумя черновиками, мобильная ночная вахта, 320 px вместе
с 200% текста и пользовательскими интервалами, чтение без JavaScript.
В CI используется предустановленный Chrome образа `ubuntu-24.04`, без `apt`
и `playwright install`. Основание: [состав образа GitHub](https://github.com/actions/runner-images/blob/main/images/ubuntu/Ubuntu2404-Readme.md#browsers-and-drivers),
[поддержка канала Chrome в Playwright](https://playwright.dev/docs/browsers#google-chrome--microsoft-edge).
Шаг браузерной проверки ограничен двумя минутами.

Общие `pnpm lint`, `pnpm test`, теги `@journal`/`@recipes`, категории,
аудиоблок, меню, карта и море не входят в этот редакционный gate.
Изменённые CSS, runtime, шаблоны, другие медиа и смешанные изменения сохраняют
обычный объём проверок. Ручное `checks=editorial` не может обойти эту границу.
Новая/изменённая строка каталога допускается только как буквальные данные
товара из выбранной публикации; изменение кода модуля этим режимом не покрыто.

## Выпуск и проверка процесса

Обычный push сам выбирает редакционный путь. После успешного Pages один раз
проверить публичный переход из анонса к записи и её товару с `?audit=...`,
затем завершить задачу. Независимое замечание к старому разделу — отдельная
задача, а не повод задерживать пост.

Ручной `checks=editorial` всегда является репетицией: **не загружает
Pages-артефакт и не публикует сайт**, даже при смешанных изменениях или
неизвестной базе. При неизменных публичных файлах он выбирает
`editorial-check` и проверяет последнюю запись тем же коротким сценарием;
при более широком diff сохраняет рассчитанный объём проверок.
Полный контроль интерфейса остаётся доступен через `checks=full` для задач,
которые действительно его затрагивают.
